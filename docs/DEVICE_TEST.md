# FiilPods 真机协议验证报告

> 测试对象：FIIL Key Max（`B0:F1:AA:BB:CC:DD`），固件 `3.0.1.1`
> 测试时间：2026-10-24
> 测试工具：`tools/probe/FiilProbe`（C# / WinRT，独立于模块的第三方实现）

## 为什么这份报告重要

模块的单测（`app/src/test`）证明的是**代码逻辑**，跑在 JVM 上，协议字节由我们自己构造。
本报告证明的是**协议本身**：用一套与模块完全无关的实现（C# + Windows 原生 RFCOMM 栈）
连上真实耳机，逐条收发，看耳机是否真的按我们理解的方式响应。

两者互补。单测全绿但真机不通，说明协议理解错了；真机通但单测红，说明代码写错了。

## 连接方法

| 项 | 值 |
|---|---|
| RFCOMM UUID | `d52b47bc-2dea-42c4-b26d-20252fceeeb3` |
| 握手 | 连上后必须先发 `setUnlock`（`cid=39` `cmd=0xFF` payload `02 34`），否则耳机对所有命令静默 |
| 帧格式 | `[seq][cid][type][00][lenField][cmd][payloadLen][payload]`，`lenField >= 2` |
| 方向 | 请求 `type=01`，响应 `type=02`，通知 `type=03` |
| 响应 cid | 状态查询恒为 `0x27`（39 = QUERY）；状态变更走 `0x28`（40 = NOTIFY） |

## 测试结果

### 握手与基础

| 用例 | 发送 | 回包 | 结论 |
|---|---|---|---|
| setUnlock 握手 | `00 27 01 00 04 ff 02 02 34` | `seq=0 cid=39 type=2 cmd=255 payload=FF` | PASS |
| 版本查询 | `00 27 01 00 02 02 00` | `seq=1 cid=39 type=2 cmd=2 payload=03-00-01-01` | PASS 固件 3.0.1.1 |

### MAF 五态（`cid=44` 写 / `cid=40` 通知 / `cid=39` 回读）

逐档写入后回读，全部一致：

| 档位 | 写入 | cid=40 通知 | cid=39 回读 | 结论 |
|---|---|---|---|---|
| 0 关闭 | `00 2c 01 00 01 00` | `payload=00` | `00` | PASS |
| 1 降噪 | `00 2c 01 00 01 01` | `payload=01` | `01` | PASS |
| 2 开放 | `00 2c 01 00 01 02` | `payload=02` | `02` | PASS |
| 3 兼听 | `00 2c 01 00 01 03` | `payload=03` | `03` | PASS |
| 4 风中 | `00 2c 01 00 01 04` | `payload=04` | `04` | PASS |

**时序注意**：写完后立即查询，耳机可能仍返回旧值（DSP 切换有延迟）。测试中改为轮询
最多 6 次、每次间隔 400ms，全部通过。模块侧的状态回填依赖 `cid=40` 通知而非轮询，
因此不受此影响。

### EQ 读写（`cid=32` 写 / `cid=39 cmd=4` 读）

原始回包 12 字节：`0A 0E 08 06 04 02 00 01 FA FC FE 02`
→ `reserved=0x0A`、`type=0x0E`、十段增益 `08 06 04 02 00 01 FA FC FE 02`

| 用例 | 写入 | 回读 | 结论 |
|---|---|---|---|
| 读取 | — | 十段解析成功 | PASS |
| 第一段 8→12 | `00 20 01 00 0c 0a 0f 0c ...` | `0A 0F 0C ...` | PASS |
| 第一段 →4 | `00 20 01 00 0c 0a 0f 04 ...` | `0A 0F 04 ...` | PASS |
| 还原 | `0A 0E 08 06 ...` | 与原始完全一致 | PASS |

**关键点**：写入时 payload[0] 必须回填耳机自己给出的 `reserved` 字节（此处 `0x0A`），
不能写死 0。这与 `F046StyleFragment.s0()` 的做法一致。

### 蓝牙畅连（写 `cid=1 cmd=1` / 读 `cid=39 cmd=128`）

| 用例 | 结论 |
|---|---|
| 1→0 | PASS（重连后回读确认） |

**这里发现一个易错点**：写入必须用 `cmd=1`，`cmd=128` 只用于查询。
用 `cmd=128` 去写时，耳机会回一个 echo（看起来像成功），但状态根本不改变——
这是个会骗人的静默失败。

**另一个真机行为**：关闭畅连会让耳机主动断掉当前的 RFCOMM 链路。这不是 bug，
是耳机在回收多点连接的通道。模块的重连逻辑会自动恢复。

### 断连重连闭环

断开 → 等待 3s → 重连 → 重新 `setUnlock` → 回读，全部正常：

| 用例 | 结论 |
|---|---|
| 重连后解锁 | PASS |
| 重连后状态回读 | PASS 固件 3.0.1.1 |
| 重连后电量 | PASS `payload=00-62-00` → 98% |

## 测试过程中修正的三处测试自身缺陷

记录下来，避免以后重复踩：

1. **帧解析把 `type=01` 当成帧头**。响应帧 `type=02`，导致所有回包被丢弃，
   表现为"耳机完全静默"。改用偏移 3 的保留字节 `0x00` + 合法 `cid` 做同步。
2. **畅连写入用了查询命令值**。见上，静默失败。
3. **在断开的 socket 上继续发命令**。畅连关闭会断链，后续用例全部 `COMException`。
   把畅连测试移到 EQ 之后，并在断链后自动重连。

## 未覆盖的部分

| 项 | 原因 |
|---|---|
| 佩戴检测 | Key Max 不支持（仅 F051/F053 有该命令） |
| 自适应档位（`cid=1 cmd=14/15/16/17`） | Key Max 不支持（仅 F046/F049） |
| 多点设备列表 `cid=1 cmd=136` | 需要第二台设备配合 |
| 超级岛 / 设置页注入 / 融合设备中心 | 需要 Android 真机，Windows 无法验证 |
| LDAC 开关 | 需要 A2DP 协商，当前链路是 SPP 不涉及 |

以上功能在代码中均有实现，但未经真机验证，README 的"交付状态"章节已如实标注。
